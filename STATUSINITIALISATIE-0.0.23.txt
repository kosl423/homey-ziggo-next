Ziggo Next for Homey v0.0.23
Power status initialization

STATUS MESSAGE HANDLING
- Up to 100 MQTT status messages received before subscription acknowledgement
  (SUBACK) are buffered.
- After a successful subscription, the current connection is registered before
  buffered messages are processed in their original order.
- Pending power requests are evaluated only after the complete buffer has drained.
  This prevents an earlier status from overriding a later state in the buffer.
- Subscription rejection, buffer overflow, malformed input, and disconnection
  invalidate initialization. Callbacks from previous connections are ignored.

INITIALIZATION AND POWER REQUESTS
- Standard on/off requests wait up to 10 seconds for a valid live initial state.
- Requests for the same state share the waiting period. Conflicting requests keep
  the latest requested state and reject superseded requests.
- Additional requests do not extend the initialization deadline.
- Expiry, disconnection, and shutdown cancel pending initialization requests.
  A later status message will not execute an expired request.
- The Power button is blocked while the initial state is unknown.

RETAINED AND BUFFERED STATUS
- A retained status may be stored as an unverified diagnostic candidate.
- A retained candidate does not update Homey's on/off state, authorize a Power
  command, or confirm a pending transition.
- A valid live status replaces the retained candidate.
- Buffered live messages may initialize the current state but cannot confirm
  an uncertain command from an earlier connection or restart.

TRANSITION PROTECTION
- Standard on/off commands and the Power button share one controller per device.
- Identical requests share one transition. Conflicting requests retain only
  the latest desired state.
- Commands can be cancelled before publication if the requested or observed
  state changes.
- A pending transaction is stored before publication and is never replayed
  automatically after restart.
- Preparation is limited to 15 seconds. Status confirmation is limited to
  20 seconds from publication start. The key transport retains its 12-second
  timeout.
- An uncertain outcome blocks further transitions until a suitable live target
  status is received. Power commands are not automatically retried.
- Status changes from the physical remote remain visible without continuous
  enforcement of a previously requested state.

WARNINGS AND DIAGNOSTICS
- Device warnings indicate an unconfirmed power state or expired initialization.
- Warning updates are serialized. A valid live state or completed transition
  can clear the warning.
- Diagnostic storage is serialized and limited to 250 entries.
- Cleared diagnostic entries may reappear when another message is recorded.

PROTOCOL LIMITATIONS
- Retained messages do not establish that a reported state is current.
- No additional CPE.getUiStatus query is enabled.
- The last accepted live state remains usable during the same uninterrupted
  status connection. Disconnection or monitor replacement invalidates it.
- Status subscriptions use QoS 0 and do not guarantee delivery of every change.
- Local status ordering does not establish a Ziggo command correlation ID.
  A delayed live message cannot always be identified as outdated.
- Key commands retain QoS 2 and retain=true. These settings do not guarantee
  exactly one physical execution across the complete Ziggo service chain.
- Protection covers commands from this app; independent clients and physical
  remote actions can still change the device state.

VALIDATION
56 automated offline tests cover controller behavior, transport guards,
initialization, reconnection, cancellation, transaction persistence,
diagnostics, and concurrent requests.

The tests use simulated Homey and MQTT environments. They do not establish
Ziggo status frequency, delivery guarantees, or Homey Flow timeout behavior.
The status initialization implementation also passed offline Homey CLI
debug-level validation on October 14, 2026.
